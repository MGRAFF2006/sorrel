Quick start

The alpha already supports a complete local loop. Initialize a workspace, create a change, and submit a lane for review.

sorrel init
sorrel change create -m "Describe the change"
sorrel lane create feat/example
sorrel lane submit

Why Sorrel?

  • Snapshots and changes are first-class objects, not incidental commit metadata.
  • Lanes isolate concurrent work and preserve resumable context.
  • Policy, grants, and secret references remain authoritative in Core.
  • Git import, export, and colocated sync provide an adoption bridge.

Cohesive product direction

Hub without the dashboard

This plan combines the parts you liked into one information architecture and stays inside Sorrel’s product language.

Landing behavior

  1. A returning user resumes the last project and route they used.
  2. A project opens on Code: description, directory structure, recent change, README, members, and release context.
  3. A new or signed-out user sees a simple project/organization picker—not health metrics or dashboard cards.
  4. Inbox remains globally available with an unread badge, but it is not forced as the splash screen.

Where each idea belongs

  • Inbox is the cross-project queue for decisions: review, policy, sync, and completed work.
  • Workbench is the deep review surface once a proposal is opened.
  • Work board visualizes real Sorrel lanes through planned, active, review, and integrated states. It deliberately avoids becoming a generic issue tracker.
  • README cards carry narrative identity on projects, organizations, and user profiles.

Route model

/projects/:idCode overview and README/projects/:id/workLane board/list/projects/:id/reviewsReview queue and workbench/inboxGlobal decision queue/orgs/:idOrganization README and projects/profiles/:idUser README and activity

API honesty

Project metadata, proposals, comments, workflow runs, session state, repositories, and sync refs exist today. Directory browsing, rendered README content, rich diffs, durable Inbox state, profiles/organizations, and lane lifecycle queries require explicit Hub APIs. The UI must not infer permissions or invent authoritative state.

Suggested implementation order

  1. Project chrome + Code overview using repository metadata already available.
  2. Review workbench backed by explicit change/diff endpoints.
  3. Global Inbox aggregation and read/later/resolved state.
  4. Lane board after Hub exposes lane ownership and lifecycle truthfully.
  5. Organization/profile README rendering with safe Markdown rules.
